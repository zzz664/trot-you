# 첫 구독 등록과 최초 청구 연결

## 구현 범위

하나의 `feature/billing-initial-subscription` 브랜치에서 기존 준비 세션을 실제 공급자 프로토콜, 암호문 vault, 최초 청구 동의 화면 및 검증된 원장 확정까지 연결했다. 갱신·환불·정산 내보내기·운영 배포는 이 기능의 범위가 아니다.

- Toss v2 `requestBillingAuth` → 서버 authKey 교환 → 최초 카드 빌링, 직접 KakaoPay charged ready → approve(SID와 최초 결제 동시 반환).
- Node 표준 AES-256-GCM, 전용 32바이트 base64 키/버전, 무작위 IV, 계정·가수·공급자·환경·mandate·용도 AAD. 실제 키를 생성하거나 저장하지 않았다.
- 원래 로그인 세션·nonce·정책·금액·고객/주문 참조 바인딩, GET의 암호화 인증 코드 수집과 고정 303 query 제거, 별도 명시적 POST 결제 동의.
- 단계별 영속 claim, 처리 중/불명 결과 재발송 차단, Toss 주문 조회, Kakao TID 조회로도 SID가 없는 경우 수동 확인 유지. 확인된 승인 이후 DB 응답 유실은 상태 조회 후 동일한 DB 확정만 한 번 재시도하며 공급자 요청은 반복하지 않는다.
- 원장·SID vault·구독 유료 기간·알림 아웃박스의 원자적 commit/rollback, 가수별 최초 혜택 한 번, 만료된 미청구 idle의 소유자 복구와 안전한 재구독.
- 테스트/운영 모드 표시, PC/모바일 Kakao URL 구분, 큰 글씨 세 단계, 닫기/뒤로가기/중복 클릭/응답 유실/인증 만료/동의 변경/불명 상태 UI.
- 공급자·vault 비활성 상태에서도 현재 소유자의 안전한 DB 상태 조회/미청구 취소를 유지한다. 운영 mock fallback은 없다.

## 독립 검토와 수정

독립 보안 검토와 결제 프로토콜 검토를 각각 완료했다. 정책 잠금 대기 후 시간 재검사, 두 번의 Toss 호출을 포함하는 전체 실행 예산(서버 300초/브라우저 285초), 성공 후 재구독 방해, nonce/로그인 세션 유실 후 만료된 idle 복구, PC Kakao handoff, DB-only 확정 복구의 비동기 오류 정리, 제한된 계정의 기존 결제 조회/원장 보정 경계를 수정했다. 검토자가 최종적으로 각각 403개와 362개 관련 테스트를 별도로 통과했다(결제 검토는 별도 fixture 12개도 포함).

## 현재 검증 증거

- 로컬 전체 단위 테스트 **1,643개 통과**, 루프백 공급자 fixture Node 테스트 **12개 통과**.
- `check:all` 통과: ESLint/Prettier, 공식 DB 타입을 사용한 TypeScript, 전체 단위 테스트, 대비 검사, Next/PWA 빌드. 실제 Supabase CI run `40100263346`의 공식 생성 `database.ts`를 SHA-256 `6c910fa49e7cf8b5a56e7517c017febd1e1bd858ecd4833506fad33a85d7e5ec` 일치 확인 후 그대로 반영했다. 타입 우회나 생성 파일 수작업 수정은 하지 않았다.
- 보조 PG18/PGlite에서 전체 SQL **2,286개 ×2 통과**(신규 159개). 실제 Supabase PG17/JWT/PostgREST/동시성 증거가 아님을 구분한다.
- 실제 독립 PostgreSQL 세션 동시성 **19개 케이스**를 추가했다. 기존 125개 동시성 회귀를 유지한다. 실행은 실제 로컬 Supabase CI가 담당한다.
- 실제 앱·Supabase와 격리 루프백 공급자를 연결하는 전용 CI 브라우저 **21개 케이스**를 작성했다. 기존 기본 23개·인증 78개 회귀를 유지한다. 세 Playwright 설정의 `--list`를 확인했으며 새 enrollment 디렉터리는 기본 설정에서 제외하고 전용 격리 CI에서만 실행한다. 세 글자 크기와 모바일/PC 스크린샷 검토는 CI 산출물 단계에서 수행한다. 제한된 로컬 브라우저 실행을 재시도하지 않았다.
- 이전 마이그레이션 체크포인트의 실제 CI는 2,271개 pgTAP ×2, 125개 동시성, 1,240개 단위, 기본 23개/인증 78개 브라우저 회귀를 통과했다. 새 정책 필드·전체 앱·신규 19개 동시성·21개 브라우저 케이스의 실제 DB/브라우저/시각 검증은 최종 exact-head CI가 수행해야 하며, 위 보조 결과로 통과했다고 주장하지 않는다.

## 운영 확인 경계

기본 결제 설정은 비활성이다. 실제 가맹점/키/등록·승인·청구/환불 API, 공급자 sandbox/live, 배포 또는 운영 정책 활성화를 수행하지 않았다. 합성 단위 키와 허구 계정/약관만 테스트에서 사용했다. 실제 merchant 자격, 승인된 과세 방식, Kakao 시간 형식, 명시적으로 선택한 월 주기와 약관의 일치, 플랫폼 실행 시간, 프록시 접근 로그의 URL/credential 제거, 보관·키 교체·수동 보정·공급자 credential 해지 절차는 별도 운영 확인 사항이다.

## 명시적 상용 정책 선택

UTC/한국 시간 월 주기 및 과세 방식을 암묵적 기본값으로 운영에 사용하지 않는다. 승인된 불변 정책에 `billing_period_calendar`(UTC 또는 Asia/Seoul의 월말 보정)와 `payment_tax_basis`(지원 범위: VAT 포함 과세 원화)를 명시해야 등록이 가능하다. 기존 정책의 미설정 값은 실패로 닫히며 새 승인 버전이 필요하다. 테스트에만 선택 값을 명시했고 실제 설정을 활성화하지 않았다. UTC 2월 28일과 한국 시간 3월 1일이 다른 월 경계를 갖는 회귀 테스트를 포함한다.

## 실제 CI 회귀 수정

실제 앱 체크포인트 CI `40101415712`에서 DB 2,286개 ×2, 독립 동시성 144개, 공식 타입 drift 없음, 품질 및 기본 브라우저 23개가 통과했다. 인증 브라우저의 6개 실패는 기존 `SameSite=Strict` 기대값과 의도된 provider GET 복귀용 `Lax` 계약의 불일치였고, 독립 보안 재검토 후 기대값을 수정했다. HttpOnly·HTTPS Secure·경로 제한·Origin POST·계정/원래 세션/nonce 검증은 완화하지 않았다.

신규 브라우저는 16/21개 통과했다. Kakao 4개 실패는 합성 공급자가 모바일/PC에 같은 URL을 반환하면서 테스트는 구분 표식을 기대한 fixture 오류였다. 합성 URL만 구분하고 실제 공급자 URL은 변경하지 않는다. 마지막 실패에서 발견된 실제 제품 문제는 결제 응답 유실 후 준비 전용 ‘청구되지 않는다’ 문구를 재사용한 점이었다. 등록/결제 전용 오류 문구를 분리하고 이미 결제되었을 가능성·상태 조회·재결제 금지를 명시했다. 이전 승인 여부와 준비 요청 자체의 효과도 구분한다. 모든 오류 코드 회귀와 실제 ledger 한 건을 유지한 상태 조회 복구 검증을 추가했다.

실패 스크린샷과 갤러리도 확인했다. 앱 문구를 가리는 Next 개발 표시기는 공식 `devIndicators: false` 설정으로 비활성화하되 앱 오류나 실제 내용을 숨기지 않는다. 수정된 불명 결과/복구 화면은 다음 exact-head CI에서 새 스크린샷을 확인해야 한다. 브라우저를 로컬에서 재실행하지 않았고 실제 결제/공급자 요청도 수행하지 않았다.

수정 후 `check:all` 전체가 통과했다(단위 1,658개). 루프백 fixture 13개도 통과했고 독립 결제·보안 재검토에서 추가 차단 문제는 없었다. 실제 브라우저 재검증과 새 시각 증거는 수정 커밋의 CI 결과로만 확정한다.
