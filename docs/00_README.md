## 2. 기획안과 달라진 점 (반드시 읽을 것)

기획안은 네이티브 앱(Flutter/RN) + 인앱 결제를 전제로 썼다. 기술 스택이 **Next.js 웹**으로 확정되면서 아래가 바뀐다. 각 항목의 상세 근거는 `01_architecture.md` 2장에 있다.

| 항목 | 기획안 | 이 설계 | 왜 |
| --- | --- | --- | --- |
| 앱 형태 | iOS·Android 네이티브 앱 | **PWA(홈 화면 추가형 웹앱)** | Next.js 스택. 스토어 심사 없음 → 11/30 가능 |
| 결제 | 스토어 인앱 결제 | **PG 정기결제(빌링키)**: 카드 기본 + 카카오페이·휴대폰 | 웹앱은 인앱 결제 불가. PG는 결정 사항의 결제 수단 3종을 모두 지원 |
| 첫 달 1,000원 | 스토어 인트로 오퍼 | 서버에서 첫 회 청구액을 다르게 계산 | PG 정기결제는 회차별 금액 지정 가능 |
| 정산 공제 | 앱마켓 수수료(15~30%) | PG 수수료(약 3% 내외) | 가수에게 돌아가는 금액이 오히려 커진다 → 정산률 재협상 여지 |
| 푸시 | FCM·APNs | **Web Push(VAPID)** + 카카오 알림톡 | iOS도 홈 화면 추가 시 Web Push 지원. 도달 보장은 알림톡이 담당 |
| 로그인 | 카카오 SDK 직접 연동 | Supabase Auth의 Kakao 프로바이더 | 세션·토큰 관리를 Supabase에 위임 |
| 배치 | 별도 배치 서버 | Vercel Cron + Supabase 함수 | 서버 운영 부담 제거 |

> **스토어 앱이 꼭 필요해지는 시점**(앱스토어 노출, 인앱 결제 요구)에는 같은 코드를 Capacitor로 감싸서 올린다. 결제 모듈은 처음부터 `PaymentProvider` 인터페이스 뒤에 두므로 그때 스토어 결제 구현체만 추가하면 된다. (`04_payment_settlement.md` 참고)

## 4. 설계 원칙 (전 문서 공통)

1. **재사용성**: 도메인 로직은 `src/server/services/`에 한 번만 쓰고, Route Handler·Server Action·Cron이 모두 그것을 호출한다. UI는 `src/components/ui/`의 기본 컴포넌트를 조합한다.
2. **확장성**: 외부 의존(결제, 푸시, 알림톡, 저장소)은 인터페이스 뒤에 둔다. 가수 수·구독자 수가 늘어도 저장 구조가 바뀌지 않게 한다(메시지 1회 저장, `{이름}` 치환은 조회 시).
3. **일관된 코드 품질**: `06_coding_standards.md`의 규칙을 ESLint·TypeScript strict·Prettier·테스트로 강제한다. 사람이 리뷰하기 전에 도구가 먼저 거른다.
4. **하드코딩 금지**: 숫자·문구·URL·키는 `app_settings` 테이블, `src/config/`, 환경 변수, i18n 메시지 파일 중 하나에만 존재한다. 코드 본문에 리터럴이 나오면 ESLint가 실패한다.
