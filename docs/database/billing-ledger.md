# Subscription and verified-money database foundation

This migration is a database capability, **not a working payment integration**. It makes no HTTP requests, charges, refunds, provider registrations, live transactions or credential changes. There is no checkout, scheduler, payment service, credential encryption adapter, webhook processor or settlement implementation yet. Payments remain disabled by the existing application configuration.

## Data boundaries

| Object                                | Purpose and access                                                                                                                                                                                                                                       |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `public.subscriptions`                | One persistent identity per user + artist; paid/grace dates, provider enum and lifetime introductory redemption. Owner and unrestricted admin read, no direct client/server mutation grant. Artist accounts cannot read another fan's subscriptions.     |
| `private.payment_mandates`            | Subscription-owned provider/environment/merchant snapshot, opaque customer and secure-store UUID references, consent version. Service read only; registration through RPC. No SID, billing key, auth token, raw provider payload or invented ciphertext. |
| `private.billing_obligations`         | Immutable-in-practice financial/policy snapshot and mutable processing state. Unique subscription + period start; at most one open obligation per subscription. RPCs never change the amount, interval or provider/mandate snapshot.                     |
| `private.payment_attempts`            | Stable order/idempotency UUID, ordinal, lease and `created → inflight → success / failed / unknown` lifecycle. An attempt is not money.                                                                                                                  |
| `public.payment_events`               | Append-only verified charge (+) or refund (−), integer KRW, safe provider enum, original-charge link and period. Owner/admin read; no raw provider identifiers or credentials.                                                                           |
| `private.payment_event_verifications` | Server-only evidence reference and provider action ID, unique within provider + test/live environment + merchant account. Charge ties to exactly one attempt; refund has its own action ID.                                                              |

Foreign keys intentionally prevent deleting a user/profile/artist with subscriptions or financial history. Anonymization, legal retention and secure credential revocation are separate unresolved workflows; do not solve them with cascading ledger deletion. The lifetime intro redemption is retained on the same subscription even after cancellation, expiry, provider change or refund.

`private` remains excluded from PostgREST exposed schemas. Its pre-existing schema usage grant to authenticated users supports identity helpers, **not table access**; every billing table/function explicitly revokes client privileges. A service key must stay server-only. Authenticated application admins do not acquire financial write authority.

## Trusted RPC contract

All `billing_*` functions require the actual database role `service_role`, explicit EXECUTE grants and pinned empty `search_path`. Being a profile admin, supplying a forged JWT metadata role or merely knowing an attempt ID does not authorize them. Service-role direct INSERT/UPDATE/DELETE/TRUNCATE grants are also revoked for new billing tables. Ledger mutation triggers additionally reject UPDATE/DELETE/TRUNCATE by ordinary owner SQL; a database superuser can still change schema and is outside the application threat model.

1. **`billing_open_subscription(user, artist, provider)`** requires a completed, unrestricted profile and an active artist. It creates or returns the same pending identity, or reopens an expired/canceled identity after paid access ends and unresolved obligations are cleared. It preserves lifetime introduction/history. No new paid access is granted.
2. **`billing_register_mandate(subscription, environment, merchant, customer_ref, credential_ref, consent_version)`** records an opaque reference for a pending episode. A different active mandate conflicts rather than silently switching providers. A secure credential adapter must later issue and resolve the UUID; this schema does not make that adapter exist. Consent recording here is not proof of legally valid consent.
3. **`billing_prepare_obligation(...)`** snapshots the exact amount, period, price version, grace seconds, retry seconds and maximum retries supplied by the future validating service. Renewal must start at the last paid end; initial/reopened periods cannot overlap the preceding paid period. Matching calls return the same UUID; changed parameters conflict. Future renewals may be prepared, but cannot be claimed before due.
4. **`billing_prepare_attempt(obligation)`** returns a stable existing nonfailed attempt. Only definitive failure permits a new attempt, subject to due time and retry bounds. Returning an ID is **not dispatch permission**.
5. **`billing_claim_attempt(attempt, lease_seconds)`** atomically changes `created` to `inflight` and returns a server-only dispatch descriptor with lease token and stored provider metadata. A competing/repeated claim returns null. The service must dispatch only from that one successful claim. Lease duration must exceed the provider timeout plus persistence margin; this foundation does not choose or execute an HTTP timeout.
6. **`billing_record_attempt_outcome(attempt, lease_token, failed|unknown, evidence_ref)`** accepts definitive failure only with an evidence reference. Inflight outcome writes require the matching token. An unknown result can later be conclusively reconciled as failed by the trusted service. Neither outcome creates revenue.
7. **`billing_finalize_charge(attempt, provider_action, amount, currency, approved_at, evidence_ref)`** accepts only inflight/unknown attempts after verification. In one transaction it inserts ledger + private evidence, marks attempt successful and obligation settled, redeems intro and updates the paid period. Exact repeats return the existing event; financial mismatches fail. A unique provider-action conflict rolls back all effects. The service must first verify the actual provider order, customer, merchant, environment, action, status, amount and currency; SQL and an opaque UUID do **not** verify a signature or authenticate a provider response. Provider timestamps must be finite and in the accepted attempt/observation interval; the attempt lower bound is floored to a second because provider approval timestamps can have seconds-only precision. Clock skew outside that interval requires reconciliation, not a fabricated timestamp.
8. **`billing_record_refund(original_charge, provider_action, positive_amount, currency, refunded_at, evidence_ref)`** records a refund that the provider has already verified. It locks the original charge, validates exact replay inputs, inserts a negative event, and caps cumulative refunds at that charge. It does not call a provider, approve eligibility or automatically revoke access.

No generic `transition_subscription(..., 'active')` exists. Paid/grace state is reachable only through narrowly scoped billing outcomes. Every mutation path affecting dispatch locks in the order subscription → obligation → attempt; cancellation locks the same subscription. Enrollment additionally locks profile → artist before subscription so restriction/pause cannot race its eligibility check. Existing mandate billing is not automatically canceled by a later profile restriction/artist pause; the future service must define that policy explicitly. No transaction holds locks over a provider HTTP request.

### Unknown is not failure

A timeout or expired lease becomes `unknown`. Calling prepare/claim after lease expiry never supplies a fresh dispatch lease or new order ID. The unknown obligation blocks retry, reopening and cross-provider fallback until authenticated reconciliation establishes the result. A process death after provider success can therefore recover the **same** attempt and finalization, without assuming the provider rejects duplicate merchant order IDs.

Toss and KakaoPay are stored separately. Neither a database UUID nor a unique merchant order proves provider-side idempotency. In particular, lost KakaoPay renewal results must not be blindly retried; merchant-approved recovery for an unknown transaction remains a launch gate. Provider switching is only possible on a new pending episode after paid access and unresolved work end, with a fresh mandate. Mid-period switching is deliberately absent.

The refund ledger cap is **not an external refund reservation**: two independent HTTP requests could both leave this database before a result is recorded. Future live refund work requires stable reserved refund operations and unknown-result reconciliation before any HTTP dispatch. There is no live refund API to misuse in this feature.

## Access, cancellation and history decisions

- Paid access is `[current_period_start, current_period_end)`. Grace access is separately `[grace_started_at, grace_ends_at)`; it does not require the previous paid end to be in the future. `has_active_access(artist)` derives the current user from Auth and checks restrictions, not a caller-supplied user ID.
- Renewal failure/unknown anchors grace to the unpaid renewal period start, not to each retry. Late workers do not create a fresh grace window. Retry counts are per obligation: one initial attempt plus `max_retries`. Only definitive failures permit retry; unknown outcomes require reconciliation. Initial-payment failures do not create access or grace.
- `cancel_subscription(id)` allows only the owner or trusted service, not an admin acting as another user. It stops new claims atomically and clears the next billing time. Paid access remains until the paid end. **Canceling during unpaid grace ends grace access immediately**; it never fabricates another paid period. There is no resume-before-paid-end action in this foundation.
- Cancellation cannot unsend a request already claimed/dispatched. Such an attempt remains reconcilable. A verified late approval is recorded exactly once and grants its paid period, while status stays canceled and future billing stays disabled. Cancellation-first prevents a later claim. No automatic provider mandate revocation is implemented.
- `billing_expire_subscription` expires canceled/grace rows at their respective boundaries. Access checks are time-based even if the expiry worker is delayed. Unresolved inflight/unknown work remains open after expiry and prevents reopening. Late verified recovery cannot overwrite a newer episode because no newer episode may start while it is unresolved.
- `first_started_at` is lifetime history; `episode_started_at` moves only on successful first payment of a reopened episode. Renewals preserve it. Old paid boundaries/history remain visible while a new episode is pending but do not grant access. The later message service should calculate its history cutoff from the **current episode**, not lifetime first-start time; this feature does not expose messages.
- A full refund does not restore introductory eligibility, erase history or silently stop billing. Entitlement changes/refund approval require a separately explicit policy and service workflow.

### Provisional policy, not operational/legal approval

The existing documented settings draft proposes KRW 6,500 monthly, KRW 1,000 introductory price once per artist/user, three days' grace, 24-hour retries (maximum three), and seven days of pre-episode message history. This migration seeds no operational settings and hardcodes none of those prices/durations into RPC behavior: the future validated settings service supplies snapshots. Monthly anniversary/end-of-month calculation remains a future pure service function; SQL enforces coherent, nonoverlapping finite intervals, not a final calendar policy.

The proposed “within seven days and unread” refund rule is **not implemented or legally approved**. Outstanding decisions include final intro/refund/retention terms, cancellation during grace, resumed-history visibility, delayed-recovery/catch-up billing, provider switching, secure credential storage/revocation, live merchant approvals, actual fees, and KakaoPay unknown-renewal recovery. Settlement will use decimal intermediates/final-only rounding in a later feature; this ledger uses exact integer KRW and cannot represent floating-point money.

## Verification and operation boundary

Run the existing local Supabase PG17 commands from [identity database setup](identity-artists.md). `npm run test:integration` runs rollback-only pgTAP suites, including 151 lifecycle, 71 independent security and the existing 140 identity tests (362 total). The new lifecycle/security suites cover privilege denials, stable identities, exact boundaries, retries/unknown, idempotent finalization, refunds and ledger immutability.

`npm run test:db:concurrency` uses independent PostgreSQL sessions inside **only the disposable local Supabase Docker container**. It proves real lock contention for double claims, cancellation/claim ordering, duplicate success, concurrent bounded refunds and a claim waiting past grace expiry (seven cases). Application RPCs execute with `SET LOCAL ROLE service_role`; owner SQL is used only for fictional setup, observation and the deliberate contention barrier, not to bypass the RPC permission checks. It requires no existing auth/subscription/ledger data; committed fictional fixtures are followed by a local reset. Do not run it against personal/shared/hosted databases. The script does not accept a remote connection URL or provider credentials.

CI runs reset, database lint, pgTAP twice, real concurrent sessions, official generated types, typecheck and the generated-type drift gate. The first feature run may intentionally fail the final drift gate after publishing `database-types`; import the genuine artifact, commit it, and rerun every gate. Never hand-edit generated `src/types/database.ts`. Schema types describe shapes, not grants.

Supplemental local PGlite/pgTAP execution (PostgreSQL 18 WASM with a synthetic Auth fixture) is useful for syntax/logic/ACL checks, but is not Supabase PG17, real JWT/PostgREST verification or multi-session proof. CI outcomes are recorded separately in the work log. The feature adds no application UI behavior; the existing quality/browser CI remains required. No staging/production migration, secret, real account, notification, payment or refund is executed.

Transactional notification outbox, provider inbox/reconciliation review history and settlement schema are later coherent features. Consequently the current atomic transaction covers recognized money plus paid state, **not notification delivery**. A future notification integration must extend that transaction with an outbox before promising eventual notifications.
